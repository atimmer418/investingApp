Today's Priorities
#1
FRED-199 — Skip the step-up auth section when it isn't enabled
On the Account Security page, users without Step-Up Authentication still see the "Security Verification" overlay flash (shield + "Please verify your identity…" + "Verifying…") during the async PIN-status check before the page loads. They should skip it entirely and land directly on the loaded security settings. Users with step-up keep the overlay and PIN prompt exactly as today. Root cause confirmed in-code: security-settings.page.ts defaults to the unauthenticated overlay at first paint (isAuthenticated=false), then awaits pinService.hasPin() before it knows whether step-up is even on — so the verify overlay paints for everyone in that window. Tier 1 — acceptance criteria already in the backlog.
Medium
Why I Picked This
FRED-199 is the strongest Tier-1 story that can ship and verify in this sandbox today. Of the four A/C-ready READY stories, two stay gated exactly as before: FRED-191 (load-perf) needs a running Capacitor build on a real device this sandbox can't provide, and FRED-195 (pig avatars) needs SVGs from the PersonalTypeshit/FRED Logo sibling directory — I re-checked this morning, still not on disk. That leaves FRED-199 and FRED-200, both build-ready here. I picked FRED-199 over FRED-200 on the Decision Framework's quick-win + guaranteed-completion rule and the difficulty bias: FRED-199 is a focused, single-page loading/gating fix I confirmed in-code (ngOnInit paints the verify overlay during the await hasPin() window), whereas FRED-200 is a 3hr+ epic that introduces Angular signals for the first time plus a localStorage snapshot — higher architectural risk, better as tomorrow's pick. Tier 1, full acceptance criteria in the backlog, no triage gap.
Strategic Alignment
The vision calls for a calm, premium, trustworthy surface with complete loading/error states and no misleading UX. A security page that flashes "verify your identity / Verifying…" at a user who has no step-up auth — then silently drops them into settings a moment later — is exactly the kind of confusing, low-trust seam to remove before private beta. Security surfaces are where polish matters most for confidence.
Production Readiness Impact
This lifts the error/loading-state coverage side of readiness directly — it replaces a misleading interim flash with an honest, distinct "checking" state and removes vestigial dead code (the unreachable "Verify Identity" button + authenticateUser() stub). Low architectural risk: one frontend page, no backend/schema/auth-logic change, tsc-verifiable here. The familiar sandbox caveat applies — the live both-path device render (390×844 / 430×932) is handed to Andrew via "Looks Good."
Implementation Options
Three ways to fix the flash. All three end with no-step-up users landing straight on settings and step-up users keeping the overlay + PIN prompt; they differ in how the interim "checking" state is modeled and what happens to the vestigial verify button. Tap one to select it; use the edit pencil on the selected card to tweak the approach before approving.
Option A Recommended
Distinct "checking" state + remove the dead button
Add a dedicated interim flag (e.g. checkingStepUp, true until hasPin() resolves). While checking, render a neutral loading indicator — a plain spinner with no "verify your identity" framing. After it resolves: step-up users get the verification overlay + promptPin('verify') exactly as today; non-step-up users go straight to the loaded settings — never seeing the overlay, and PIN users never briefly seeing settings (no content leak either direction). Delete the now-unreachable "Verify Identity" button + authenticateUser() per the no-dead-code rule.
Pros: satisfies AC-1/AC-3 cleanly (a real third state, not a guessed boolean); removes dead code (AC-5); smallest honest model; no content leak either way. Cons: introduces one new state flag + a neutral-loader template branch to maintain. Risk: Low — one frontend page, no behavior change for step-up users, no backend/auth-logic touch. Estimate: ~1–2 hrs
Option B
Reuse existing flags, keep the verify button wired
Don't add a new state — instead flip the defaults so the verify overlay only renders once a requiresStepUp flag is set true (after hasPin() resolves), showing the existing isAuthenticating spinner as the neutral interim. Keep the "Verify Identity" button + authenticateUser() and re-wire them as a manual re-verify fallback rather than deleting them.
Pros: no new field; smaller TS diff; retains a manual verify affordance. Cons: overloads existing booleans (harder to reason about the three views); the verify button simulates nothing real, so re-wiring it is busywork and AC-5 flags it as dead-ish. Risk: Low–Medium — flag overloading invites a content-leak edge case; keeps a do-nothing passkey stub in the codebase. Estimate: ~1–2 hrs
Option C
Single "ready" gate before first paint
Hide the entire content behind one ready boolean: compute hasPin() first, render only a neutral skeleton until it resolves, then show either the verify overlay or settings. Simplest template, but one boolean can't cleanly distinguish "checking" from "verify," so it risks either a blank flash or — if mistimed — a settings content-leak for PIN users.
Pros: fewest template branches; conceptually simple. Cons: weakest on AC-3's explicit "distinct checking state" requirement; a single gate is the most likely to leak content one direction or blank-flash the other. Risk: Medium — collapsing checking and verify into one flag is exactly the ambiguity AC-3 asks us to avoid. Estimate: ~1 hr

Potentially Out of Scope

UX Considerations
  • Three states, one honest path — checking (neutral spinner) → verify overlay (step-up only) → settings. The interim indicator must NOT use the "verify your identity / Verifying…" framing — that's the whole bug.
  • It's a network call — hasPin() hits GET /user/pin/status; keep the interim state honest and avoid flashing settings content for PIN users (content-leak both directions).
  • Error path — hasPin() currently fails open (network error → treated as no-PIN). Preserve unless Andrew says harden (Q1).
  • Mobile-first — verify both paths at 390×844 and 430×932; no overlay clip, no layout shift between the checking spinner and the loaded settings.
Questions For Andrew
From the story (a): hasPin() currently fails open on a network error — a failed PIN-status call is treated as "no PIN," so during an outage a step-up user could slip past the gate. Preserve that fail-open behavior (default, safer for availability), or harden it to fail-closed (block / retry on error)? My recommendation: preserve fail-open — a transient status error shouldn't lock a user out of their own settings. Required
From the story (b): the "Verify Identity" button (HTML L27–30) + authenticateUser() (TS L160–167) are vestigial — a 1.5s setTimeout passkey simulation that never runs in the real flow. OK to delete them as part of this story (no-dead-code rule)? My recommendation: yes, delete — they're unreachable and simulate nothing real. Optional
