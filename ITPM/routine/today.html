FRED-187 — Investigate Plaid paycheck-triggered investment flow
Can FRED trigger an investment the moment a user's paycheck actually lands in their bank — detected via Plaid — instead of relying only on the user-declared pay cadence? This is a research / feasibility spike: read the existing integration, study the Plaid mechanisms, and deliver a written verdict + recommendation + phased build outline. I ground-truthed the current state this morning:
  • Plaid is wired with AUTH + IDENTITY products only (PlaidService.java:57) — purely bank-linking + ACH-relationship setup. There is no TRANSACTIONS / INCOME product and no Plaid webhook endpoint today.
  • Triggering is schedule-based: the 11:55 PM cron scans for schedules whose nextInvestmentDate is due (see INVESTMENT_SCHEDULER.md), and PaydayNotificationService already predicts "your paycheck hits tomorrow" off that stored cadence — it never observes the actual deposit.
So this story is genuinely net-new capability research, not a tweak. Tier 2 — no acceptance criteria in the backlog yet, so I've drafted them below for you to approve or edit; the build won't start until they're confirmed.

Implementation Options
Option A Recommended
Spike centered on Plaid Transactions /transactions/sync + webhook detection
Investigate adding the TRANSACTIONS product to the existing Link flow, a Plaid webhook endpoint that fires on SYNC_UPDATES_AVAILABLE, and classifying inbound payroll credits via personal_finance_category (INCOME_WAGES) / the recurring-transactions stream. The doc recommends this as the leading mechanism and sketches how a detected credit enqueues an InvestmentExecution through the existing batch-funding path with dedup. Most general (works for any linked bank) and reuses Plaid we already integrate.
Pros: broadest bank coverage; builds on the Link flow we already own; no new vendor; clearest path to "invest the day the money lands"; deliverable fully producible in-sandbox. Cons: requires payroll-classification heuristics (false-positive risk) and a new public webhook endpoint to secure; detection lag between posting and Plaid visibility must be handled. Risk: Low for the spike itself (it's research); the heuristics/latency are the real risks the doc must quantify before any build. Estimate: ~2–4 hr (write-up)
Option B
Spike centered on Plaid's dedicated Income / Payroll product
Investigate Plaid's purpose-built income detection (/credit/bank_income or the recurring-transactions income stream), which classifies recurring payroll for you rather than relying on home-grown heuristics. The doc would assess fit, accuracy, and onboarding/consent impact.
Pros: far more reliable payroll classification out of the box; less custom heuristic code to maintain; designed exactly for this use case. Cons: likely an additional Plaid product cost and extra user consent/onboarding friction; may be heavier than needed if Transactions-sync already suffices — the spike must confirm availability + pricing before committing. Risk: Medium — recommending it commits FRED to a paid product and more onboarding steps; only worth it if classification accuracy clearly beats Option A. Estimate: ~2–4 hr (write-up)
Option C
Spike centered on a "confirm-the-deposit" check layered on the existing schedule
Don't move to true event-driven detection. Instead investigate a smaller change: on the user's already-predicted payday, do a one-shot Plaid transactions/balance lookback to confirm the paycheck actually landed before releasing the ACH pull — keeping the current schedule as the source of truth. The doc would weigh this lower-ambition path against A/B.
Pros: smallest eventual build; no webhook infrastructure; reuses the schedule model; directly reduces the "pulled before payroll posted" failure mode. Cons: not truly "triggered by the paycheck" as the story asks — it's confirmation, not detection; still depends on the user declaring a cadence. Risk: Low — but may under-deliver on the story's intent; best framed as a fallback/phase-1 the doc can recommend if A/B prove too heavy. Estimate: ~2–3 hr (write-up)
