Today's Priorities
#1
FRED-186 — Update API searches to use debounce and switchMap
Make the app's as-you-type searches that hit the backend fire one debounced, cancellable request instead of one per keystroke. I ground-truthed this morning that three search inputs call the network on every keystroke with no debounce and no cancellation, so a slow earlier response can land after a newer one and overwrite it (a stale-result race), and each keystroke spams the API:
  • lump-sum-investment stock search — (ionInput)="searchStocks()" → two /alpaca/assets calls (equity + ETF) per keystroke, Promise-based, no cancel.
  • portfolio-customize stock search — same double /alpaca/assets pattern per keystroke.
  • my-profile referral-code validator — (input)="onReferralCodeInput(...)" → raw .subscribe on /user/referral/validate, no debounce / distinctUntilChanged / switchMap. Notably, FRED-114's AC-1 already specified this exact validator should use distinctUntilChanged + switchMap — so this is closing a documented gap, not new design.
The fourth searchbar — stockselection — filters a pre-loaded in-memory asset list (no network call), so switchMap doesn't apply there; that's the one open scope question below. Tier 2 — no acceptance criteria in the backlog yet, so I've drafted them below for you to approve or edit; the build won't start until they're confirmed.

Strategic Alignment
The production-readiness mission lists bug-free core flows and no placeholder UX explicitly. A stale-result race on the referral validator can show "valid" for the wrong code, and stock searches that flash older results read as buggy — both erode trust, FRED's primary business driver after retention. Debounced, switch-mapped searches feel instant and correct, and they cut needless load on the Alpaca-backed /alpaca/assets endpoint. This also reuses an RxJS pattern already present in the codebase (app.component.ts uses debounceTime(300) + distinctUntilChanged), keeping the design system consistent rather than inventing a new approach.
Production Readiness Impact

The main risk to manage is behavioral regression at the async boundary: converting Promise-based searchStocks() calls into RxJS streams means the isSearching spinner, empty-state clearing, and min-length guards must keep behaving exactly as today, and a failed request must not kill the stream for the next keystroke. Frontend-only, no backend/schema/auth change; tsc/ng build-verifiable in-sandbox.   • AC-1 — The three per-keystroke network searches are converted to a debounced, switch-mapped RxJS pipe: lump-sum-investment searchStocks (the equity + ETF /alpaca/assets calls), portfolio-customize searchStocks, and my-profile onReferralCodeInput. Implementation Options
Option A Recommended
Per-component RxJS pipe — a Subject per search, debounceTime(300) → distinctUntilChanged → switchMap, mirroring the app's existing pattern
In each of the three components add a searchInput$ = new Subject<string>(); the (ionInput)/(input) handler calls .next(value) instead of invoking the async search directly. Subscribe once in ngOnInit with debounceTime(300) → distinctUntilChanged() → switchMap(term => httpCall) → takeUntil(destroy$), moving result assignment into the subscription. For the two stock searches, fold the equity + ETF /alpaca/assets calls into a single forkJoin inside the switchMap so both are cancelled together. Catch errors inside the inner observable so the stream survives. This is the same idiom already in app.component.ts and the one FRED-114 specified for the referral validator.
Pros: fixes the stale-result race correctly (switchMap cancellation, AC-2); reuses an in-codebase pattern (design consistency); minimal blast radius — three localized components; frontend-only, fully tsc/ng build-verifiable here. Cons: each component's Promise-based searchStocks becomes stream-based, so the spinner/empty-state wiring must be moved into the subscription and re-verified per page. Risk: Low–Medium — well-understood RxJS; main risk is missing an isSearching/empty-state edge, caught by static review + live check. Estimate: ~2–3 hr
Option B
Shared search utility / directive applied across all the searches
Extract a single reusable helper (an operator factory debouncedSearch(fn) or a small directive) that wraps the debounceTime → distinctUntilChanged → switchMap chain, then apply it at each call site so the pipe lives in one place.
Pros: DRY — the pipe is defined once; future searches get it for free. Cons: over-engineering for three call sites with slightly different request shapes (single validate call vs forkJoin of two asset calls); adds an abstraction the vision explicitly warns against ("never introduce unnecessary abstraction"); harder to read than the inline idiom already used in app.component.ts. Risk: Medium — the shared abstraction has to flex for both request shapes; more design surface than the problem needs. Estimate: ~3–4 hr
Option C
Debounce only — add debounceTime, keep the Promise-based calls (no switchMap)
Wrap the existing searchStocks() / validator in a debounce timer so it fires less often, but leave the underlying await ... toPromise() / .subscribe calls as-is.
Pros: smallest diff; cuts request volume. Cons: rejected — doesn't fix the core bug. Without switchMap cancellation, two debounced requests can still overlap and the slower-but-older one can overwrite the newer result (the stale-result race). It also fails the story's explicit "switchMap" requirement. Risk: High (of being wrong) — leaves the actual race condition in place. Estimate: ~1–2 hr (but non-compliant)

In Scope
  • Convert the three network-hitting searches to Subject → debounceTime(300) → distinctUntilChanged → switchMap: lump-sum-investment stock search, portfolio-customize stock search, my-profile referral validator.
  • Fold each stock search's equity + ETF /alpaca/assets calls into one cancellable inner observable (forkJoin).
  • Preserve min-length guards, isSearching spinner, empty-state clearing, and error handling exactly as today.
  • Clean up via takeUntil(this.destroy$); tsc + ng build clean; verify at 390×844 / 430×932.
Potentially Out of Scope
  • The stockselection searchbar — it filters a pre-loaded in-memory list, no API call, so switchMap is N/A (Q1; recommend leaving as-is, with at most a small render-only debounce).
  • Any backend / endpoint change to /alpaca/assets or /user/referral/validate — this is purely a frontend request-orchestration fix.
  • Non-search debounce opportunities (e.g. window-resize, scroll) — not "API searches," not in scope.
  • Broader RxJS refactor of the affected components beyond the search pipe.
UX Considerations
  • Perceived speed — 300ms debounce should feel instant; results appear once after the user pauses, not mid-type flicker.
  • No stale flash — with switchMap, an abandoned query's late response is discarded; the list only ever shows the latest term's results.
  • Spinner correctness — isSearching turns on when a request starts and off when its result (or error) lands, even when an earlier request was cancelled.
  • Error resilience — a failed request shows the existing empty/error treatment but must not break the stream for subsequent keystrokes.
  • Mobile-first — verify at 390×844 and 430×932: searchbar keyboard behavior unchanged, results list scrolls as before.
