Today's Priorities
#1
FRED-188 — Add null userId guard to processChat()
The non-streaming Ask Fred path can throw a server error on a null userId. I ground-truthed it in the code this morning: ChatService.processChat() loads the user with userRepository.findById(request.userId()) at ChatService.java:85 with no null guard — and Spring Data's findById(null) throws InvalidDataAccessApiUsageException. The sibling method streamChat() already guards it correctly at ChatService.java:215 (request.userId() != null ? userRepository.findById(...).orElse(null) : null). The fix is to mirror that exact guard in processChat(). Backend-only, ~1 line. Tier 2 — no acceptance-criteria block in the backlog yet, so proposed A/C is below for your approval before the build runs.
Easy

Tier 1 is exhausted for this sandbox, so I dropped to Tier 2 and picked the strongest quick win. With no build-ready Tier-1 story left, I picked FRED-188 — yesterday's named #2 next-pick — a latent crash-class bug I verified directly in the code this morning: processChat() calls findById(request.userId()) unguarded while streamChat() already guards the identical call. Easy, guaranteed completion, backend-only, ./gradlew build -x test-verifiable here, with a proven sibling to mirror. Tier 2 — proposed acceptance criteria below for your approval; the build won't start until they're confirmed.
Strategic Alignment
The mission is production readiness — bug-free core flows. Ask Fred is a core surface, and POST /api/chat is the documented fallback for the SSE stream (FRED-183). A null userId reaching that fallback would surface as a 500 instead of a graceful guest answer — exactly the kind of latent failure you don't want discovered in private beta. Hardening it reinforces trust and reliability on the chat experience.
Production Readiness Impact
Closes a latent crash-class defect on the chat fallback path (bug-density lever) by mirroring an already-shipped, already-verified guard from the sibling method. Tiny and contained — one statement in one backend file, no schema / API-contract / frontend change, ./gradlew build -x test-verifiable in-sandbox — so it lifts correctness with effectively zero regression risk and is fully verifiable here without a device.

Implementation Options
Option A Recommended
Mirror streamChat()'s exact guard
Replace the unguarded two-line Optional<User> userOpt = userRepository.findById(request.userId()); … User user = userOpt.orElse(null); at ChatService.java:85–88 with the same ternary streamChat() uses at line 215: User user = request.userId() != null ? userRepository.findById(request.userId()).orElse(null) : null;. One backend file, byte-for-byte consistent with the proven sibling.
Pros: smallest correct diff; identical to an already-verified guard; the two chat methods read the same; zero regression surface. Cons: leaves the guard duplicated across the two methods (addressed by Option C). Risk: Very low — one statement, backend-only, gradle-verifiable here. Estimate: ~10–15 min
Option B
Explicit early null-branch
Keep the Optional shape but wrap it: User user = null; if (request.userId() != null) { user = userRepository.findById(request.userId()).orElse(null); }. Same effect, a touch more verbose, arguably clearer intent — but diverges from streamChat()'s idiom.
Pros: explicit and readable; same runtime behavior as A. Cons: the two chat methods now guard the same call in two different styles — minor inconsistency on identical logic. Risk: Very low. Estimate: ~10–15 min
Option C
Extract a shared loadUserOrNull(request) helper
Same fix as A, but pull the guarded load into one private helper used by both processChat() and streamChat(), removing the duplicated guard entirely. DRY/hardening win that prevents the two from drifting again.
Pros: single source for the guard; the two methods can't diverge in future. Cons: also edits streamChat() (currently correct) — wider blast radius than a one-bug quick win warrants. Risk: Low, but touches a working method for a refactor that isn't the bug. Estimate: ~25–35 min
