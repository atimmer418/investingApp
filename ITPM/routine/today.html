Acceptance Criteria (already in backlog)
FRED-203 is a Tier 1 story — it already has a full acceptance-criteria block in backlog.md, so there's nothing to approve here. Shown for reference; the build verifies against these.
  • AC-1 — In editMode the page renders the shared blue hero header (blue gradient + concave white cutout + centered white title + back button) — the same blue-hero-header security-settings uses — on both step 1 and step 2.
  • AC-2 — The blue header renders only in editMode; onboarding mode (editMode = false, "Identity Verification") keeps its existing non-blue header, and the blue-hero styles do not leak into onboarding.
  • AC-3 — The editMode header reuses theme/_blue-hero-header.scss via @use (not a re-implemented copy); back button calls existing goBack(); title is "Edit Identity".
  • AC-4 — In editMode the user cannot proceed part 1 → part 2 unless at least one step-1 field changed from its on-file value: the continue button is disabled AND proceedToStep2() is a no-op while step 1 still equals the prefilled values.
  • AC-5 — "Changed" = current step-1 form value vs a snapshot of the Alpaca-prefilled values captured after the prefill HTTP resolves (re-typing the same value is not a change); existing !step1Valid validation still applies.
  • AC-6 — Gating applies only in editMode; onboarding step 1 → step 2 is unaffected.
  • AC-7 — The existing localStorage step-1 draft restore and step-transition animation still work; a restored draft equal to on-file values counts as "not changed."
  • AC-8 — npx tsc --noEmit exits 0; verified at 430×932: editMode blue header on both steps, onboarding original header, part-1 gate enables/disables correctly.
Implementation Options
Option A Recommended
Reuse the shared partial via @use + *ngIf="editMode" header swap + prefill-snapshot gate
In the template, wrap a new .blue-hero-header block (matching security-settings' markup — hero-nav / back-btn / centered header-title "Edit Identity" / back-btn-spacer) in *ngIf="editMode", rendered above both step 1 and step 2; keep the existing onboarding header for !editMode. SCSS does @use '../../theme/blue-hero-header' — because the class only exists in the editMode branch it's naturally scoped, so no styles leak into onboarding. For the gate: capture step1Snapshot = JSON.stringify(step1Form.value) right after the Alpaca prefill resolves (the on-file baseline), add a get step1Changed() that compares the live value to it, and in editMode disable the continue button ([disabled]="!step1Valid || !step1Changed") and early-return from proceedToStep2() when editMode && !step1Changed.
Pros: reuses the single-source header partial (no gradient duplication — passes the "literal count == 1" guard); naturally scoped to editMode; small additive TS; mirrors the proven security-settings header; onboarding path untouched. Cons: correctness depends on capturing the snapshot at the right moment (after the Alpaca prefill resolves, not after the localStorage draft restore). Risk: Low — frontend-only, tsc/ng build-verifiable here; live 430×932 render confirmed by you. Estimate: ~1–2 hr
Option B
Same header, but gate on the form's dirty state
Identical header work as A, but detect "changed" with Angular's built-in step1Form.dirty / pristine instead of a value snapshot.
Pros: less code — no snapshot to capture or compare. Cons: fails AC-5/AC-7. dirty flips on any keystroke even if the user re-types the same value back, and the localStorage draft restore (patchValue) also marks the form dirty — so a no-op edit or a restored on-file draft would wrongly unlock the gate. Risk: Medium — subtly wrong; violates the "re-typing the same value is not a change" requirement. Estimate: ~1 hr
Option C
Extract a reusable <app-blue-hero-header> component + snapshot gate
Same snapshot gate as A, but wrap the header in a small shared <app-blue-hero-header [title]> component (driven by the partial) that KYC editMode consumes — and that other settings pages could adopt later.
Pros: cleanest call-site; a reusable header component for future pages. Cons: new component is wider scope than this one-page story needs; the SCSS partial is already the single source, so a component wrapper adds indirection — mild scope creep. Risk: Low–Medium (scope creep beyond the story). Estimate: ~2–3 hr

FRED-203 — KYC edit page: blue hero header + part-1 gating
In Scope
  • Add the shared blue hero header (via @use 'theme/blue-hero-header') to kyc-verification in editMode only, on both step 1 and step 2; title "Edit Identity", back button → existing goBack().
  • Scope the header so it does not leak into onboarding mode (one component serves both flows) — gate via *ngIf="editMode" so the class only exists when editing.
  • Capture a snapshot of step-1 values after the Alpaca prefill resolves (the on-file baseline); add a step1Changed diff.
  • Block part 1 → part 2 in editMode until a step-1 field changes: disable the continue button AND make proceedToStep2() a no-op while unchanged (existing !step1Valid still applies).
  • Preserve the localStorage step-1 draft restore + step-transition animation; a restored draft equal to on-file counts as "not changed."
  • npx tsc --noEmit exits 0; ng build within budget.
Potentially Out of Scope
  • Changing the onboarding ("Identity Verification") header in any way — it keeps its existing non-blue header.
  • Restyling the KYC input fields themselves (that's FRED-202 territory) — this story is the header + the gate only.
  • Any change to the Alpaca PATCH submit logic / KYC update API contract.
  • Extracting a reusable header component — only if you pick Option C; otherwise the shared SCSS partial is enough.
UX Considerations
  • EditMode header — blue gradient + concave white cutout, centered "Edit Identity", back button on the left, consistent on both step 1 and step 2; matches security-settings / my-profile.
  • Gate / disabled state — the continue button reads clearly disabled (greyed) until a real change is made, including while the Alpaca prefill is still in flight (no baseline yet). Onboarding's continue is unaffected.
  • Onboarding unchanged — verify no blue-header bleed and identical onboarding step 1 → step 2 behavior.
  • Mobile-first — verify at 390×844 and 430×932: header cutout aligns, title centered, no clipped labels.
