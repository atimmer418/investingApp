Today's Priorities
#1
FRED-200 — Always-loaded tab3 stat strip via a signals service
The tab3 Freedom stat strip (Freedom date / Freedom age / To go) re-runs three separate fetches on every cold load — getUserProgress(), getPortfolioDashboard(), getKycData() — coordinated in loadStatStrip(). It shows — dashes until all three settle, caches nothing across tab navigation, and doesn't reflect a My Profile edit until the component is recreated. Move the data + the freedom-date/age/dollars-away math into a dedicated singleton FreedomStatsService built on Angular signals (the app's first signals usage — an intentional, approved pilot), kept warm across navigation and hydrated instantly from a user-scoped localStorage snapshot on cold launch, auto-updating when an input changes. Tier 1 — full acceptance criteria already in the backlog, with Andy's approach decisions recorded.
Hard
Why I Picked This
FRED-200 is now the only build-ready Tier-1 story left for this sandbox — and it was flagged as today's likely pick yesterday. It just was never checkmarked, so it still sits in READY — it needs closing out, not building (see Tomorrow's Pick). That leaves FRED-200. Difficulty bias allows it: readiness is 78 (> 75), so Hard work is now in tolerance, and FRED-200 has Andy's approach already decided (dedicated service + signals + a localStorage snapshot), so it's well-shaped. Tier 1, no triage gap.
Strategic Alignment
The vision demands a calm, premium, instant surface with complete loading states and no placeholder UX. The Freedom stat strip is the emotional core of tab3 — it's the user's "when am I free?" number — and today it greets them with — dashes on every cold launch and again on each tab re-entry. Making it instant (and self-updating after a My Profile edit) directly serves retention and trust, the top two business priorities. It also lands a deliberate, well-bounded signals pilot that informs the app's future reactive direction.
Production Readiness Impact
This lifts loading-state coverage and perceived performance on the most-visited surface: no dash-flash on cold launch (hydrated from a snapshot), no second cold round on re-entry, and a strip that reflects edits without a manual reload. Risk is contained — one new singleton service plus a tab3 refactor, frontend-only, no backend/schema/auth change, tsc-verifiable here. The first-signals-usage is the one architectural watch-item, mitigated by scoping it to a single bounded service. Sandbox caveat applies: the live cold-launch / re-entry / post-edit device render (390×844 / 430×932) is handed to Andrew via "Looks Good."

So these options vary on what's still genuinely open: how much to ship in one pass, and whether to honor the signals decision. Full build to the A/C — signals service + cold-launch snapshot
Build exactly what Andy decided. A new singleton FreedomStatsService owns the three fetches and the freedom-date/age/dollars-away math (preserved byte-for-byte from loadStatStrip()): toSignal(userProgress$) bridges progress, writable signals hold equity + birth-year, a computed() derives the stats plus a loading signal. FRED-200 — Always-loaded tab3 stat strip via signals service
In Scope
  • New frontend/src/app/services/freedom-stats.service.ts (providedIn:'root') owning the three fetches + the freedom-date/age/dollars-away math currently inlined in loadStatStrip(); math preserved exactly — 4% target (retirementIncome / 0.04, $1.5M default), client-side freedom-year projection, freedomAge = freedomYear − birthYear, dollarsAway = max(0, target − equity) — identical displayed numbers (AC-1).
  • Signals as the reactive primitive: toSignal(authService.userProgress$) via @angular/core/rxjs-interop; writable signals for equity + birth-year set via .set(); a computed() for the stats + a loading signal; tab3 renders from the signal. A short comment marks the first signals usage / approved deviation from the BehaviorSubject convention (AC-2).
  • Delete the old orchestration from tab3 — progressDone/portfolioDone/kycDone, tryRender(), the manual subscribe/takeUntil for the strip — removed, not commented (AC-2, AC-9).
  • Always loaded across navigation: the singleton holds the computed stats, so leaving and returning to tab3 shows the last values instantly — no — dashes, no second cold round of three fetches (AC-3; re-entry refresh policy — see Q1).
  • Auto-update on My Profile save: after saveChanges() succeeds, the strip reflects new monthly-investment / retirement-income values with no manual reload — via loadUserProgress() → userProgress$ → the toSignal bridge (and/or an explicit refresh()) (AC-4).
  • Preserve FRED-196 resilience verbatim: the KYC fetch keeps timeout(10_000) + bounded transient-only retry (TimeoutError / status 0 / status ≥ 500, never 401/403/404); Freedom Age degrades honestly; Freedom Date + To Go render independent of the KYC outcome (AC-5).
  • User-scoped localStorage snapshot of the displayed values; cold launch hydrates and paints real numbers immediately, then a background refresh corrects them; keyed/validated to the current user; cleared on logout alongside the JWT/data clear; a missing/corrupt/foreign snapshot falls back to the normal — loading state. Stores derived display values only — no tokens or new PII (AC-8).
  • Keep feeding liveEquity — the FRED-195 pig-avatar input on tab3 — unbroken (AC-7).
  • cd frontend && npx tsc --noEmit exits 0, scoped build passes, no orphaned imports / dead destroy$ plumbing (AC-9).
Potentially Out of Scope
  • Migrating any other BehaviorSubjects to signals — this is a single-service, bounded pilot only; don't spread the pattern this run.
  • The MFU contribution-based projection — kept intentionally separate from tab3's income-based freedom year (AC-6); do not read or converge it.
  • Reworking the FRED-195 pig-avatar wiring — just keep liveEquity fed; no refactor.
  • A CONTEXT.md "signals convention" rewrite — note the pilot in a code comment; leave any doc/standards change for a follow-up once the pattern is proven.
UX Considerations
  • Cold launch (snapshot present) — real numbers paint immediately, no —; the background refresh swaps fresh values in quietly with no visible flicker.
  • First-ever load (no snapshot) — the loading signal shows the existing — placeholder; never NaN / undefined.
  • Error / empty — null or zero equity → To Go falls back via max(0, …); a failed userProgress or portfolio fetch degrades gracefully (no crash, no user eject, no raw error string).
  • User safety — a logged-out or switched user must never see another user's figures; the snapshot is keyed to / validated against the current userId and cleared on logout (mind the FRED-199 ordering lesson: clear the snapshot BEFORE userId is wiped).
  • Mobile-first — verify at 390×844 and 430×932; the three tiles must not shift between snapshot hydration and fresh data (keep the existing min-height).
Questions For Andrew
Re-entry refresh policy. AC-3 says returning to tab3 shows the cached values instantly with "no second cold round of three fetches" (no dashes). Should the service silently background-refresh on re-entry (stale-while-revalidate — show cached instantly, refetch quietly, swap when fresh data returns) so equity stays current after an investment runs — or NOT refetch on re-entry at all until something explicitly changes (e.g. a My Profile save)? My recommendation: silent background refresh — instant cached paint, quiet revalidate, never a dash on re-entry. Required
Snapshot staleness cap. On cold launch the strip hydrates from the localStorage snapshot, then background-refreshes. Should the snapshot have a max age beyond which it's ignored (fall back to — instead of showing a stale number) — or always hydrate then immediately revalidate regardless of age? My recommendation: no hard TTL — always hydrate then refresh right away; a stale value is corrected within seconds, and offline a slightly-stale real number beats dashes. Optional
