Today's Priorities
#1
FRED-196 — tab3 Freedom Age blanks on a flaky KYC call
Make the Tab 3 stat strip's Freedom Age tile resilient. Today, its only data source — the Alpaca GET /alpaca/account/kyc call that supplies the user's birth year — silently blanks the tile to "—" whenever that call fails or returns no DOB on a weak connection, while the other two tiles (Freedom Date, To Go) still render real values. Give Freedom Age its own transient-only retry and an honest "unavailable" state so a brief Alpaca hiccup doesn't make the strip look half-broken. Frontend-only, additive change in tab3.page.ts — no backend, schema, or auth. Verifies with tsc --noEmit in-sandbox. Tier 1 — acceptance criteria already in the backlog.
Medium
Why I Picked These
You skipped FRED-100 (RAG chunks), so I re-ran the pick with it excluded. FRED-196 is the strongest Tier-1 story that can actually ship and be verified in-sandbox today. It's a tightly-scoped, additive frontend resilience fix that hardens the error-state coverage of the Tab 3 stat strip just shipped in the FRED-192 rework — so it builds directly on finished work. The other A/C-ready stories are gated: FRED-191 (load-perf) needs a running Capacitor build on a real device this sandbox can't provide; FRED-195 (pig avatars) needs SVGs from the PersonalTypeshit/FRED Logo sibling directory that lives outside this repo; FRED-194 (uniform settings headers) is a large 9-page UI overhaul that can't be visually verified without a browser; FRED-101 (emailer) is founder-gated on an email provider + SMTP creds; FRED-169 (14-day trial) is App Store Connect config, not code. FRED-196 has no such gate. Tier 1 — full acceptance criteria already in the backlog, no triage gap. Medium difficulty, guaranteed one-day completion.
Strategic Alignment
Tab 3 is the most-visited settings surface, and its new stat strip is the first thing a user sees there. A tile that silently blanks on a weak connection reads as "this app is buggy" — exactly the trust erosion FRED can't afford right before private beta, where retention and trust are the top business priorities. Many real users will hit flaky cellular connections, so a single dropped Alpaca call shouldn't make a freshly-shipped feature look half-broken. This fix makes the strip degrade honestly (retry, then a clear "unavailable" state) instead of failing quietly — turning a fragile surface into a dependable one.
Production Readiness Impact
This lifts the error-state-coverage component of the readiness score directly — "complete loading / empty / retry / error states" is an explicit production-readiness requirement, and the Freedom Age tile is a concrete gap in it. It's low-risk: additive, frontend-only, no backend or schema change, and it reuses the existing loadUserProgress retry pattern rather than inventing a new one. A guaranteed one-day completion that keeps the readiness score climbing toward the 75 threshold without taking on any Hard work, while making a high-traffic surface dependable before beta.
Implementation Options
Three ways to scope FRED-196. All three give the Freedom Age tile a transient-only retry and an honest failure state; they differ in how much of the rest of the strip's resilience rides along. Tap one to select it; use the edit pencil on the selected card to tweak the approach before approving.
Option A Recommended
Freedom-Age-only fix, mirroring the existing retry pattern
Add a bounded, transient-only retry to the KYC observable in tab3.page.ts — retrying on TimeoutError / HTTP status 0 / status ≥ 500 only, never 401/403/404 — copying the retry shape loadUserProgress already uses. Track a distinct Freedom-Age state (loading / value / missing-DOB "—" / failed-"unavailable") so a genuine pre-KYC user still shows a plain "—" while a real failure shows an "unavailable" treatment with a retry affordance. Keep the render gate settling via finalize so a permanently-failing KYC call can never hang the strip. Exactly the A/C, nothing more.
Pros: smallest change; meets every A/C item; reuses an in-repo pattern; frontend-only, tsc-verifiable. Cons: the other two tiles keep their current (shared) error handling — not touched this run. Risk: Low — additive, scoped to one tile's data path; happy path byte-for-byte unchanged. Estimate: ~2–3 hrs
Option B
Option A + extract one shared transient-retry helper
Everything in Option A, but factor the transient-retry policy (the "retry on Timeout / 0 / ≥500, never on 4xx" logic that loadUserProgress and now KYC both want) into a single shared RxJS operator/helper, so the duplication doesn't drift over time. Freedom Age and loadUserProgress both consume the one source of truth.
Pros: removes a copy-paste retry pattern; future calls get a consistent policy for free. Cons: touches loadUserProgress (working code) to route it through the helper — slightly wider blast radius. Risk: Low–Medium — refactoring a live path; mitigated by keeping behavior identical and tsc-checking. Estimate: ~3–4 hrs
Option C
Per-tile resilience for all three stat tiles
Decouple all three stat-strip calls so each tile (Freedom Date, To Go, Freedom Age) has its own independent loading / value / failed-retry state, not just Freedom Age. A flaky call on any of the three then degrades gracefully on that one tile instead of relying on the shared gate. The most robust strip, but it expands scope beyond the A/C's Freedom-Age focus.
Pros: most robust; no tile can silently blank; consistent UX across the whole strip. Cons: largest; touches all three data paths and the render gate; goes past what the A/C asks for. Risk: Medium — broader rework of working code; cuts against the guaranteed-completion + minimal-change bias. Estimate: ~4–6 hrs
Triage Findings
FRED-196 — tab3 Freedom Age blanks on a flaky KYC call
In Scope
  • Add a bounded, transient-only retry to the KYC fetch (GET /alpaca/account/kyc) in tab3.page.ts — retry only on TimeoutError / HTTP status 0 / status ≥ 500; never on 401/403/404 — mirroring the retry shape loadUserProgress already uses.
  • Give Freedom Age a distinct state machine: loading → value (valid DOB) / missing-DOB (pre-KYC user shows the normal "—", no error treatment) / failed (after retries exhausted — a visually distinct "unavailable" state with a retry affordance, never identical to the empty placeholder).
  • Keep the render gate opening once all three calls settle (e.g. via finalize) so a permanently-failing KYC call can't hang the strip.
  • Leave Freedom Date and To Go untouched — they render from /user/progress + /portfolio/dashboard regardless of KYC outcome.
  • Preserve the happy path exactly: with a valid DOB, Freedom Age = resolvedFreedomYear − birthYear.
  • cd frontend && npx tsc --noEmit exits 0.
Potentially Out of Scope
  • Per-tile resilience for Freedom Date and To Go — that's Option C; Option A keeps the fix to Freedom Age as the A/C specifies.
  • Any backend change to the Alpaca KYC endpoint or its error responses — frontend-only this run.
  • Re-architecting how the three calls are orchestrated beyond what's needed to keep the gate non-hanging.
  • The earlier my-profile pattern that loads the same data — not modified unless a shared helper is chosen (Option B).
  • Any change to the visual design of the stat strip beyond the new failed/retry treatment.
UX Considerations
  • Failed vs empty must look different — a genuine pre-KYC user (no DOB) shows the calm "—" with no error styling; a real load failure shows an "unavailable" treatment with a retry affordance. The two must never be visually identical.
  • Loading state — Freedom Age should read as "still loading" until its call settles, distinct from both the value and the failed states; no flash of "—" before the retry chain finishes.
  • No layout shift — the failed/retry treatment must fit the existing .stat-tile footprint (the strip already uses min-height to prevent shift) at 390×844 / 430×932.
  • Retry affordance — keep it subtle and on-brand (FRED palette, Manrope); a small tap-to-retry on the tile, not a disruptive banner. Confirm the exact treatment in the questions below.
