FRED-204 — Fix the white flash in the static→Lottie reauth transition
You skipped FRED-167 (the Ask FRED redesign) — here's a fresh single story, and this one's a small, concrete fix to a defect you reported yourself. On a cold start (most visible when reauth keeps the loading cover up), the cover swaps its static fallback image for the coin-drop Lottie and a brief (~0.1s) white flash shows through. I ground-truthed the exact cause this morning:
  • frontend/src/index.html:73 hides the static fallback (#app-resume-cover-fallback) synchronously the instant lottie.loadAnimation() returns (line 65) — before the Lottie paints its first frame.
  • In that gap the white #app-resume-cover background (background:#ffffff, line 34) is exposed → the flash.
The fix is a single event-ordering swap: hide the static fallback only after a lottie-web render event, so the static image holds until the animation is actually on screen. It's frontend-only (just index.html) — no backend, schema, or auth — and directly advances current priority #3 (loading / transition states). Tier 1 — the 6-point acceptance criteria are already in the backlog, so this is build-ready; pick an approach below.

Implementation Options
Option A Recommended
Hide the static fallback on the Lottie's DOMLoaded render event
In index.html's cover script, remove the synchronous if (fallback) fallback.style.display='none' that runs right after lottie.loadAnimation() returns (line 73). Instead register window._fredCoverAnim.addEventListener('DOMLoaded', function(){ fallback.style.display='none'; }). DOMLoaded fires once lottie-web has actually built the animation's SVG in the DOM (first frame present), so the static fred-logo.svg holds until the coin-drop is on screen — the white #app-resume-cover background is never exposed. Fallback-safety is inherent: if the Lottie 404s or fails to parse, DOMLoaded never fires and the static image simply stays (AC-4). No change to the cover show/hide lifecycle. ~3 lines.
Pros: smallest possible change; deterministic; fallback-safe by construction (the hide only ever runs inside the render handler); no timing guesswork; matches AC-2/AC-4 exactly. Cons: relies on lottie-web emitting DOMLoaded — it does for any valid animation; a pathological "loads but never emits" would keep the static up, which is the desired safe fallback anyway. Risk: Low — a pure event-ordering swap, no lifecycle or Angular change; correctness provable by reading the event flow. Estimate: ~15–20 min
Option B
Hide on the first enterFrame event (self-detaching handler)
Same idea, but listen for the animation's first enterFrame (an actual paint tick) rather than DOMLoaded, then remove the listener after it fires once. This waits for a real rendered frame, not just the SVG being inserted into the DOM.
Pros: fires on a genuine paint tick — marginally stronger "truly on screen" guarantee than DOM insertion. Cons: enterFrame fires every frame, so the handler must detach itself after the first call (a touch more code); in practice DOMLoaded already means the SVG is in the DOM and about to paint, so the extra guarantee is mostly theoretical. Risk: Low. Estimate: ~20 min
Option C
Cross-fade the static fallback out (belt-and-suspenders)
Keep both layers; on the render event, add a short CSS opacity transition (~150ms) that fades the static fallback out, then set display:none on transitionend — so even a single-frame gap is masked by the fade. AC-3 explicitly says a short cross-fade is "acceptable but optional."
Pros: smoothest possible handoff; masks any residual sub-frame gap. Cons: more moving parts (a CSS transition + a transitionend handler + the display:none) for a defect the hard swap in A already fixes; if transitionend ever fails to fire, the layer lingers — needs its own guard. Over-engineered for a ~0.1s flash. Risk: Low–Medium — the extra transition machinery is more surface than the problem needs. Estimate: ~30–40 min
