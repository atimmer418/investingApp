#1
DEV-198 — Eliminate package-lock.json libc-field churn in diffs
Stop package-lock.json from producing noisy, environment-specific diffs that have to be hand-reverted to keep PRs clean. npm writes platform metadata — os / cpu / libc — into the optional-dependency blocks of the lockfile, and the emitted lines differ across the three environments that touch it: this itpm routine cloud sandbox, local, and GitHub Actions CI. I ground-truthed this morning:
  • frontend/package-lock.json has 266 os/cpu/libc entries (26 of them libc); the root ./package-lock.json has 16.
  • This sandbox runs npm 10.9.7 / node 22.22.2. CI (verify.yml) uses actions/setup-node@v4 with node-version: '22' but no pinned npm version, then runs npm ci --legacy-peer-deps. Neither package.json declares engines or packageManager. So the leading root cause is npm-version drift across environments emitting these fields differently.
This is dev-tooling hygiene that affects the routine's own PRs (the verifier flagged it on 2026-06-15). Tier 2 — no acceptance criteria in the backlog yet, so I've drafted them below for you to approve or edit; the build won't start until they're confirmed.

Strategic Alignment
A deterministic, reproducible build is an app-store launch-readiness criterion and a trust signal for investor/diligence review. Right now every routine run risks a noisy lockfile diff that has to be manually reverted before a PR is clean — friction that slows the ITPM pipeline and invites mistakes. Fixing it once makes npm ci emit a byte-identical lockfile across the sandbox, CI, and local, which keeps PRs honest and the build reproducible-from-repo — directly in line with FRED's "nothing one-off, everything reproducible from source control" principle.
Production Readiness Impact
Indirect but real: deterministic lockfiles harden the build/CI pipeline (reproducible builds are a launch-readiness lever) and remove a recurring source of human error in the release flow. No application code is touched, so user-facing risk is near zero. The one technical risk to manage is optional native-binary resolution — rollup/esbuild ship platform-specific binaries as optional deps, so the fix must NOT simply strip or omit optional deps; it must keep npm ci --legacy-peer-deps + ng build working. Fully tsc/ng build-verifiable in-sandbox, plus a direct proof: regenerate the lockfile here and confirm zero os/cpu/libc churn.

Implementation Options
Option A Recommended
Pin one npm version across all three environments (sandbox, CI, local)
Add "packageManager": "npm@10.9.7" to package.json (Corepack-enforced — the node-22 default npm), enable Corepack locally, and update verify.yml + auto-pr.yml to pin/enable the same npm before npm ci (e.g. corepack enable or npm i -g npm@10.9.7). Then regenerate both lockfiles once so they're emitted by the pinned version. This targets the root cause: identical npm everywhere → identical os/cpu/libc emission everywhere.
Pros: fixes the root cause, not the symptom; no app-code or dependency change; reproducible builds everywhere; small, well-understood diff (package.json + 2 workflows); fully verifiable in-sandbox by regenerating the lockfile. Cons: requires editing the CI workflows (Q2) and standardizing on one npm version that local devs must match; Corepack npm support has occasional rough edges to confirm. Risk: Low — version pinning is standard practice; verified by a clean lockfile regen + npm ci + ng build. Estimate: ~1–2 hr
Option B
Repo .npmrc settings only (no CI edit)
Add a committed .npmrc with stabilizing settings (e.g. engine-strict + a documented npm version, or optional-dep handling) to nudge consistent emission without touching the workflows.
Pros: lightest touch; no workflow change; one small new file. Cons: .npmrc does not directly govern os/cpu/libc field emission, so it may not fully eliminate the churn; the only .npmrc knob that removes the fields is omitting optional deps — which would break the rollup/esbuild native binaries (fails AC-6). Risk: Medium–High of not actually fixing it (the fields are version-driven, not config-driven), or of breaking native builds if optional deps are omitted. Estimate: ~1 hr
Option C
Normalize hook — a script that canonicalizes the lockfile after install
Add a small script (run via a pre-commit hook and a CI check) that strips/canonicalizes the os/cpu/libc fields after every npm install, so the committed lockfile is stable regardless of which npm produced it.
Pros: works no matter what npm version a contributor runs; can also gate PRs with a "lockfile is normalized" check. Cons: adds a new tooling/maintenance surface (a script + hook) the vision warns against ("never introduce unnecessary abstraction"); editing the lockfile out-of-band can drift from what npm would actually write and mask real changes; more moving parts than the problem needs. Risk: Medium — brittle long-term; a hand-edited lockfile can diverge from npm's source of truth. Estimate: ~2–3 hr
