Today's Priorities
#1
FRED-193 — Remove dark mode (force the app light-only for now)
Strip dark mode from the app so every surface renders in light styling regardless of the device's OS Dark Mode setting. The visible offenders are the tab-switcher, tab1, tab2, and the AI chat page — but because the global background flips drive dark app-wide, the clean fix is to remove the dark CSS across all of it. Concretely: delete the @media (prefers-color-scheme: dark) blocks from the four named surfaces, neutralize the two global flips in theme/variables.scss and global.scss, and remove the dark scrollbar blocks plus the stray monthly-freedom-update dark block. The theme infrastructure in settings.service.ts ('light' | 'dark' | 'auto', applyTheme(), the body.dark toggle) stays in place so a future story (FRED-146) can build a proper, WCAG-AA dark mode without burning that bridge. Frontend SCSS-only; grep + tsc/build verifiable in-sandbox. Tier 1 — acceptance criteria already in the backlog.
Medium
Why I Picked These
FRED-196 shipped and you closed it out, so I re-ran the pick over the remaining Tier-1 stories. FRED-193 is the strongest one that can actually ship and be verified in this sandbox today. The other A/C-ready stories are gated: FRED-191 (load-perf) needs a running Capacitor build on a real device this sandbox can't provide; FRED-195 (pig avatars) needs SVGs from the PersonalTypeshit/FRED Logo sibling directory that lives outside this repo; FRED-194 (uniform settings headers) is a large 9-page UI overhaul with a wide blast radius that can't be visually verified without a browser. FRED-193 has no such gate — it's a clean SCSS removal whose footprint I verified directly (a grep for prefers-color-scheme: dark returns exactly the 7 SCSS files the A/C names, plus settings.service.ts which is the theme infra we intentionally keep — no surprise files). Tier 1, full acceptance criteria in the backlog, no triage gap. It's also a prerequisite that unblocks the future FRED-146 dark-mode epic, which scores high on the Decision Framework (dependency chains + quick win + guaranteed completion). Medium difficulty, one-day completion.
Strategic Alignment
The product vision is explicit: "Light mode forced — color-scheme: light on every component," and dark mode is a rejected/premature pattern to be done only after every screen is migrated. Right now a user on an OS set to Dark Mode sees a half-broken, partially-inverted app — dark backgrounds bleeding through some surfaces while others stay light. That inconsistency reads as "unfinished" exactly when we're hardening for private beta, where trust and a polished, consistent surface are the priority. Forcing the app fully light now removes that seam everywhere and gives the eventual FRED-146 dark mode a clean, properly-designed foundation instead of the naive auto-inverted blocks we have today.
Production Readiness Impact
This lifts the UI-coverage / no-placeholder-UX side of readiness directly — "polished UI everywhere, no half-dark surfaces" is a concrete production-readiness requirement, and the inconsistent dark bleed is a visible gap in it across four high-traffic surfaces (tab-switcher, tab1, tab2, AI chat). It's low-risk: SCSS-only removal, no backend, schema, auth, or behavior change, with the theme infrastructure preserved so nothing is foreclosed for the future. A guaranteed one-day completion that keeps the readiness score climbing while staying squarely in the Easy/Medium band the difficulty bias calls for at this stage.
Implementation Options
Three ways to scope FRED-193. All three end with the app rendering fully light on a dark-set device and the theme infrastructure preserved; they differ in how the dark CSS is retired and whether we add a forward guardrail. Tap one to select it; use the edit pencil on the selected card to tweak the approach before approving.
Option A Recommended
Spec-exact surgical removal
Do precisely what the A/C enumerates: delete the @media (prefers-color-scheme: dark) blocks from the four surface SCSS files (tabs.page.scss, portfolio-dashboard.component.scss, retirement-planning.component.scss, ai-chat.page.scss); remove/neutralize the global flips in theme/variables.scss (~L11) and global.scss (~L181); remove the dark scrollbar blocks (global.scss ~L676/L702) and the stray monthly-freedom-update.component.scss block (~L683). Clean removal — no empty @media wrappers, no orphaned vars, no commented-out blocks. Leave settings.service.ts theme infra fully intact; hide/disable any dark toggle surfaced in settings UI. Grep proves zero remaining dark blocks; tsc/build verify.
Pros: smallest faithful diff; meets every A/C item exactly; fully verifiable in-sandbox; no tech debt left behind. Cons: no forward guardrail — a future stray dark block could re-introduce bleed (low likelihood). Risk: Low — SCSS-only, no behavior change; the happy light path is unchanged. Estimate: ~2–3 hrs
Option B
Option A + a root light-lock guardrail
Everything in Option A, plus enforce color-scheme: light at the root (index.html / :root) so even a future stray or third-party dark rule can't flip the app while we're light-only. A durable belt-and-suspenders that makes "light-only" a hard invariant, not just an absence of dark CSS.
Pros: can't silently regress to dark; codifies the vision's "light mode forced" as an enforced rule. Cons: slightly beyond the A/C; the FRED-146 dark-mode epic will need to lift this lock when it ships. Risk: Low — a single declarative line; well-understood. Estimate: ~2.5–3.5 hrs
Option C
Gate the dark blocks behind body.dark instead of deleting
Rather than delete the dark CSS, re-scope every block under body.dark (never set now that auto resolves to light), leaving the rules dormant but retained for the future dark-mode rebuild. Preserves the old styling as reference material.
Pros: keeps the existing dark styling on hand for FRED-146. Cons: violates AC-4 (no dead/dormant dark code, clean removal) and leaves tech debt; FRED-146 explicitly wants a fresh WCAG-AA palette, "not auto-inverted," so the retained blocks have no real value. Risk: Medium — dormant CSS is easy to re-activate by accident and muddies the "light-only" intent. Estimate: ~3–4 hrs
Triage Findings
FRED-193 — Remove dark mode (force light-only for now)
In Scope
  • Remove the @media (prefers-color-scheme: dark) blocks from the four named surfaces: tabs.page.scss, portfolio-dashboard.component.scss, retirement-planning.component.scss, ai-chat.page.scss.
  • Remove / make inert the global dark flips in theme/variables.scss (~L11) and global.scss (~L181) so they no longer darken any page background.
  • Remove the dark scrollbar blocks (global.scss ~L676/L702) and the stray monthly-freedom-update.component.scss block (~L683).
  • Clean removal — no empty @media wrappers, no orphaned SCSS variables, no commented-out dark blocks left behind (CONTEXT.md no-dead-code rule).
  • Preserve the theme infrastructure in settings.service.ts ('light' | 'dark' | 'auto' type, applyTheme(), the body.dark toggle and its matchMedia listener); effective default stays light.
  • If a dark/theme toggle is surfaced anywhere in settings UI, hide or disable it for now (confirm whether one exists during the footprint audit).
  • cd frontend && npx tsc --noEmit exits 0; the scoped build passes with no new SCSS/TS warnings.
Potentially Out of Scope
  • Building any actual dark palette — that's FRED-146, a multi-day epic this story intentionally unblocks but does not start.
  • Removing the theme machinery in settings.service.ts — it stays for the future dark-mode rebuild.
  • Touching prefers-color-scheme: dark blocks beyond the named A/C set if any are discovered — surface them as a follow-up rather than silently expanding scope (architectural-drift rule).
  • Migrating hardcoded hex to semantic tokens — that's part of the FRED-146 dark-mode work, not this removal.
UX Considerations
  • Verify on a dark-set device — the whole app must render in light styling with a device/OS set to Dark Mode, checked specifically on tab-switcher, tab1, tab2, and ai-chat: backgrounds, cards, text, borders, bubbles, and tab bar all identical to Light Mode, with no dark/near-black background, dark border, or inverted text anywhere.
  • No half-dark surfaces — because the global flips currently drive dark app-wide, the audit must confirm no page is left partially dark after removal (scrollbars included).
  • Settings toggle — if a light/dark control is visible in settings, it must not advertise a mode that no longer does anything; hide/disable it for now.
  • No regressions to light mode — light is and remains the default; the happy path should look byte-identical to today on a light device.
